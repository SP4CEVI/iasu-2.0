# Проектирование механизма привязки карты к студенту

Данный документ описывает процесс связывания физического носителя (студенческого пропуска с UID) с профилем конкретного студента в системе.

## 1. Кто и где осуществляет привязку

Привязкой карт занимается исключительно **Администратор** (сотрудник, отвечающий за работу с системой). 

Процесс происходит в **Веб-админ-панели**, а не в мобильном приложении преподавателя. Это сделано в целях безопасности, чтобы исключить возможность подмены или ошибочной привязки карт на стороне аудитории. Преподаватель лишь сканирует карту, которая уже привязана к студенту.

## 2. Необходимые условия (Предусловия)

Перед тем как привязать карту, администратор должен располагать следующими данными:
1.  **Физическая карта** (студенческий пропуск на базе MIFARE Plus), чтобы считать её UID.
2.  **Профиль студента**, который уже создан в системе (внесены ФИО, группа).
3.  **Бумажное согласие** студента на обработку персональных данных (номер и дата документа), так как привязка UID является частью обработки ПДн.

## 3. Как происходит считывание UID при привязке

Так как админ работает с веб-панелью (на компьютере), он не может считать NFC-метку напрямую через браузер (без сложных манипуляций с Web NFC, которые не везде поддерживаются). 

Поэтому считывание UID происходит одним из двух способов:
*   **С помощью смартфона администратора:** В админ-панели есть раздел выдачи кодов, но для считывания UID используется специальный режим или приложение.
*   **С помощью любого стороннего NFC-сканера (или терминала):** Админ подносит карту к считывателю, получает UID (например, `04:XX:XX:XX`) и вручную вводит его в форму в админ-панели (либо копирует из буфера обмена).

## 4. Диаграмма последовательности

Диаграмма отображает взаимодействие Администратора с Веб-панелью и Сервером при добавлении нового студента или привязке новой карты к уже существующему студенту.

```mermaid
sequenceDiagram
    autonumber
    actor Admin as Администратор
    participant Web as Веб-админ-панель
    participant Reader as Считыватель / Смартфон
    participant Card as Студенческий пропуск
    participant API as Сервер (REST API)

    Note over Admin: Админ получает бумажное<br/>согласие от студента

    Admin->>Web: Открывает форму "Добавить студента"<br/>или "Редактировать студента"
    
    Admin->>Reader: Подносит карту для считывания
    Reader->>Card: Радиосигнал 13.56 МГц
    Card-->>Reader: Передача UID
    Reader-->>Admin: Показывает UID (например, на экране сканера)
    
    Admin->>Web: Вводит ФИО, Группу, номер и дату согласия
    Admin->>Web: Вводит/вставляет считанный UID карты
    Admin->>Web: Нажимает "Сохранить"

    Web->>API: POST /v1/admin/students<br/>(или PATCH /v1/admin/students/{id})
    Note over Web,API: Передаются: full_name, group_id, uid,<br/>consent_document, consent_date
    
    Note over API: Проверка: подпись админа (JWT/Session),<br/>формат UID, уникальность UID
    
    alt UID уже привязан к другому студенту
        API-->>Web: 409 Conflict (Duplicate UID)
        Web-->>Admin: Ошибка: "Эта карта уже привязана к другому студенту"
        
    else Обязательные поля не заполнены
        API-->>Web: 400 Bad Request
        Web-->>Admin: Ошибка валидации формы
        
    else Успешная привязка
        API-->>Web: 200 OK (Студент создан/обновлен)
        Web-->>Admin: Уведомление "Студент успешно добавлен, карта привязана"
        Note over API: Запись в БД: students (full_name, uid)
    end
